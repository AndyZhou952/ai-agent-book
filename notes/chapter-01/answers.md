# 第一章 · 思考题与答案

## 1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

我会根据任务目标和当前瓶颈来选择。

如果 Agent 是个人助手，我希望它理解我的偏好和意图，因此会优先补充关于我的上下文。这不意味着把所有原始信息都塞进去，而是先进行存储、整理和加工，形成更精炼的用户理解（refined version）。

当现有工具无法实现目标时，我会从补上下文转向补工具。例如，获取每日新闻需要对应的 API，记录运动可能需要连接 Apple Watch。更多工具也可能帮助 Agent 获取关于我的信息，更好地 recognize me as a person。

如果不限定场景，我个人倾向于认为更多工具是最强大的选项。不过，具体设计仍应定位瓶颈：

- **Sensing / observation**：看不到必要信息时，补充上下文和观察信息。
- **Decision making**：已有信息仍无法正确决策时，考虑更强的模型。
- **Action**：缺少访问能力或执行手段时，考虑增加工具或相应权限。

因此，我对个人助手场景的上下文优先，与不限定条件时偏向工具的判断，来自不同的任务假设。

## 2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

一个直接的办法是设置 token 用量或上下文长度阈值，达到阈值时再做压缩与 summarization。

压缩时保留之前的思考信息和关键节点，去掉不再需要的冗余细节，例如因格式问题产生的重复失败调用。大块中间结果可以外置，需要时再检索；也可以考虑用子 Agent 隔离，让部分中间过程不进入主 Agent 的上下文。

我不倾向于每轮都压缩：这可能损害性能，还会引入压缩调用和 recaching 的额外开销。相比之下，按阈值触发更合适。

## 3. ★★ “模型即 Agent” 范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

并不是所有工作都需要高度灵活的工作流。有些工作需要探索、反复尝试；另一些工作有固定流程，适合由 Harness 通过 hard code 施加 constraint。

模型在工具调用决策上更自主，意味着中间过程可以减少人工细化。例如，遇到 error 时，模型可以自行判断如何处理，并独立完成一部分任务。

但对于要求严格遵循 A→B→C 的流程，我仍然倾向于用 Harness 限定执行顺序、排除其他路径。即使 Agent 自己也能完成这条流程，框架约束仍能提升安全性和稳定性。

因此，模型的自主性与 Harness 的价值可以共存：模型承担更灵活的决策，框架约束具有不确定性的输出和执行过程。我认为框架的核心价值主要体现在安全性与稳定性上。

## 4. ★★ 消融实验中 “工具结果反馈” 的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？

除了工具结果缺失，以下情况也可能让 Agent 反复尝试：

- 工具一直返回同样的 error。
- 模型出现幻觉，调用不存在的工具。
- Context window compression 丢失中间状态。
- 任务在当前条件下本来就无法完成。

我会设置最大迭代次数等停止条件，并检测重复调用：不仅看工具名，还比较传入的参数是否相同或高度相似。

当重复调用或连续失败达到设定阈值后，停止继续重试，并升级到 human-in-the-loop，由人工接管。

## 5. ★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？

以我使用 DeepSeek 时的体验为例：

- **感知**：我感觉它获取的信息主要来自国内网站，对外网信息的提取，以及 OCR 或视觉信息的利用，还有提升空间。
- **行动**：我使用过它的 thinking 模式和 web access 功能，其中网页访问提供了搜索与读取网页的手段。
- **策略**：从我能看到的思考轨迹与调用过程看，它有时会先做一轮网页调用，再继续点进具体页面。

有时它似乎无法读到网页内容。我猜测这可能与沙盒或安全限制有关，也可能与我理解中的开源、免费产品定位有关，但这只是我的推测。

如果让我改进，我会重点增强外网数据源的访问，以及 OCR 和视觉信息识别，使这些信息更容易进入任务处理过程。

## 6. ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？

我倾向于混合模式。用户输入的 query 很多样、很复杂，很难只靠固定输入形式覆盖；同时还要考虑 jailbreak（越狱）等输入风险。

Agent 可以负责理解用户表达，把自然语言需求转换成规则或工具能够理解的结构化形式；工具侧则承载相应的规则和约束。例如，涉及退款时，需要处理退款的触发条件与上限，并把用户请求转换成相关工具能接受的参数。

因此，我希望把灵活的需求理解与规则约束结合起来，而不是让整个系统只依赖其中一种方式。

## 7. ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

我会在可能产生高风险的工具调用之前增加一层检查，例如用一个小型风险分类器（risk classifier）做初步筛查，判断这次操作会影响系统，还是只涉及无关紧要的文件。

风险评级不应只看工具名称，还要结合实际调用参数。例如，同一个删除工具，删除不同文件可能有完全不同的风险。

分类器可以辅助筛查；在最终检查方式上，我更倾向于基于 rules 的确定性判断，而不是依赖模型自由判断。检查对象应主要是结构化数据，可以使用正则等规则进行校验，以尽量减少提示注入通过自然语言操纵判定结果的机会。

## 8. ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是 “开放式” 的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

我认为，在高风险或监管要求非常严格的场景中，受限的动作空间可能比开放式动作空间更合适。

## 9. ★★ 人工干预机制要求 Agent 能 “优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？

根据我的观察，有些产品会等待一小段时间，例如一两分钟，再判断能否在缺少用户回复时继续处理。

如果可以做出较有把握、符合用户期待的 assumption，可以先把假设明确列出，再据此推进可逆、低风险的部分。如果缺失信息是必要条件，或操作敏感，就应总结当前状态，暂停相关工作并交回用户。

我的处理原则是：

- 先完成可逆的低风险部分。
- 把高风险部分及未决事项记录下来，方便人类决策和 Agent 后续恢复。
- 可以通过异步消息、邮件等方式通知用户，并设置超时策略。
- 指令模糊时先澄清意图。
- 高风险操作未得到确认时暂停，不能因用户超时未回复就默认执行。

## 10. ★★★ 引言指出 “好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

### 我首先想到的例子：显式 ReAct 提示

我首先想到的是早期 ReAct 的显式提示方式：通过 prompt 要求模型先思考、输出相应的思考轨迹，再进行工具调用。当时工具调用也可能出现格式问题。

随着大量后训练，一些模型已内化了相应的推理与行动能力，因而不一定还需要用同样严格的 prompt 逐步要求它“先思考，再行动”。不过，对复杂任务，我仍认为可以通过 prompting 引导模型拆分任务。

### 我认同的参考答案例子

以下两个例子来自参考答案，我认为也符合自己的设想。

1. **要求提示词和全部工具定义必须预先放在上下文开头。** 早期模型指令遵循能力有限，提示或工具定义离开熟悉的位置后，可能难以正确识别和执行；放在轨迹中间也可能增加查找成本。Skills 在运行时按需加载提示，动态工具发现也会在找到新工具后追加定义。随着模型指令遵循能力增强，以及针对动态加载的后训练，我认为不再需要把“所有提示和工具定义都固定放在开头”作为普遍要求。
2. **通过严格的约束采样，强制工具调用符合指定格式。** 早期模型容易生成 illegal JSON 或遗漏参数，这类措施可以作为可靠性补丁；随着格式遵循能力提高，它的额外收益可能降低。

另外，外部知识库的使用方式，以及是否必须采用标准工具调用格式，也可以作为继续思考的例子。我目前只记录这些方向，尚未展开论证。
